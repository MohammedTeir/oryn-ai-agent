# Credential storage foundation

This module is not connected to onboarding, a Gemini client, logging, export, or an API-key validation flow. It must not be treated as a completed security or setup feature. Integration requires human security review, explicit user consent for saving and deletion, validation of the user-provided key, and device tests before use.

`expo-secure-store` 58.0.2 is pinned to the installed Expo SDK. Expo documents Android encryption backed by the Android Keystore; values are encrypted in app-private preferences, while the encryption key is held by the Keystore. The wrapper accepts one dedicated Gemini credential, serializes operations, rejects empty values, and returns generic errors without forwarding native exception text. The read method necessarily returns the credential to its authorized caller in process memory; callers must never log, export, include it in prompts or tool arguments, or send it anywhere other than the intended provider authentication flow. Never write it to SQLite or the feasibility evidence report. There is no fallback to plain preferences or another platform.

The SecureStore Expo config plugin points Android backup and device-transfer rules to XML excluding SecureStore preferences. `build-phone.sh` inspects the actual packaged APK with the pinned Android `aapt` and fails if the expected rules, references or exclusions are absent. No key, real or test, is included in the app or APK. Restores and reinstalls may require the user to enter a new key.

Cloud tests use an in-memory fake, including error redaction and save/delete ordering. They do not establish actual encryption, hardware backing, backup behavior, process-death behavior, invalidation handling, or absence of leaks on a physical device. A compromised/rooted phone can weaken on-device secret protection. UI confirmation, user-facing error messages, safe replacement, API-key validation, diagnostic redaction and backup/export tests remain outstanding.
